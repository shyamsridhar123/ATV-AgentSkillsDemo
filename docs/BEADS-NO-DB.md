# Beads Data Management: No-DB Mode with JSONL Storage

> How beads stores data in Beth. No fairy tales, no aspirational docs — verified against the running system.

## How It Actually Works

Beads operates in **no-db mode** (`no-db: true` in `.beads/config.yaml`). All reads and writes go directly to JSONL files in `.beads/backup/`. There is no Dolt server, no SQLite, no database process. JSONL *is* the storage layer.

This is the production configuration for Beth as of v0.60.0. It works. Doctor confirms it. Every `bd` command operates against the JSONL files.

### History: Dolt Migration

Beth originally used Dolt (a version-controlled SQL database) as the beads backend. The migration to no-db mode happened in March 2026 (epic beth-ajg). The `.beads/dolt/` directory still exists as a vestigial artifact — cleanup is tracked separately (beth-ajg.6). Dolt processes may still be running from previous sessions; they're harmless but can be killed with `pkill -f dolt`.

## Quick Setup

```bash
# 1. Install beads CLI
curl -fsSL https://raw.githubusercontent.com/steveyegge/beads/main/scripts/install.sh | bash

# 2. Initialize in your project
cd /path/to/project
bd init --prefix <your-prefix>

# 3. Enable no-db mode
# Edit .beads/config.yaml and add:
#   no-db: true

# 4. Verify
bd list          # Should return empty or existing issues
bd --version     # Should show >= 0.60.0
```

## File Structure

```
.beads/
├── config.yaml              # Configuration (tracked in git)
├── metadata.json            # Backend identity (tracked in git — see note)
├── backup/
│   ├── issues.jsonl         # All issues (the live data store)
│   ├── dependencies.jsonl   # Dependency relationships
│   ├── events.jsonl         # Audit trail / history
│   ├── comments.jsonl       # Issue comments
│   ├── labels.jsonl         # Label definitions
│   └── config.jsonl         # Internal config state
├── dolt/                    # Vestigial Dolt files (gitignored, pending cleanup)
├── hooks/                   # Git hooks
└── *.log, *.pid, *.port     # Runtime files (gitignored)
```

**What matters:**
- `config.yaml` — settings including `no-db: true` (tracked in git)
- `backup/*.jsonl` — your live data (tracked in git)
- `metadata.json` — backend identity, regenerated by `bd init` (tracked in git — the `.beads/.gitignore` does NOT exclude it, despite what older docs claimed)
- `dolt/` — vestigial, gitignored, pending cleanup

### Git Tracking Strategy

The `backup/*.jsonl` files **must be tracked in git** so issue state survives across clones and sessions. The `dolt/` directory and runtime files are gitignored by `.beads/.gitignore`.

In no-db mode, JSONL files are the live store — every write updates them directly. Commit after write operations:

```bash
git add .beads/backup/
git commit -m "sync beads state"
```

Recovery from git history is your safety net: `git show <commit>:.beads/backup/issues.jsonl`

## JSONL Record Format

Each line in `backup/issues.jsonl` is a self-contained JSON object with all fields:

```json
{
  "id": "beth-04i",
  "title": "E2E epic test-subtask check",
  "issue_type": "epic",
  "status": "closed",
  "priority": 2,
  "description": "",
  "acceptance_criteria": "",
  "created_at": "2026-03-10T05:04:09Z",
  "created_by": "Stephanie Schofield",
  "owner": "sschofield@microsoft.com",
  "close_reason": "Closed",
  "closed_at": "2026-03-10T05:04:23Z",
  "updated_at": "2026-03-10T05:04:23Z"
}
```

Dependencies live in `dependencies.jsonl`:
```json
{
  "issue_id": "beth-04i.1",
  "depends_on_id": "beth-04i",
  "type": "parent-child",
  "created_at": "2026-03-10T00:04:12Z",
  "created_by": "Stephanie Schofield"
}
```

Events (audit trail) in `events.jsonl`:
```json
{
  "id": 1,
  "issue_id": "beth-a3m",
  "event_type": "created",
  "actor": "Stephanie Schofield",
  "created_at": "2026-03-07T13:02:25Z"
}
```

No relational joins. No query layer. Plain text you can grep, jq, or read with your eyes.

## Data Workflow

In no-db mode, writes go directly to JSONL. No `bd backup` step is needed after writes.

```bash
# After creating/closing/updating issues — just commit
git add .beads/backup/
git commit -m "sync beads state"
```

> **Note:** `bd backup` and `bd backup restore` still exist for Dolt-mode workflows. In no-db mode, `bd backup` is a no-op since JSONL is already the live store.

## Commands

### Closing Issues (Beth Workflow)

In Beth's workflow, issues are closed through the enforcement layer, not `bd close` directly:

```bash
npx beth-copilot close <id>       # Preferred — runs enforcement checks
```

This calls `bd close` under the hood but adds validation (e.g., checking acceptance criteria).

### Creating Issues

```bash
# Simple task
bd create "Fix login redirect" -l in_progress

# Epic for complex work
bd create "Auth system overhaul" --type epic -p 1

# Subtask under an epic
bd create "JWT token rotation" --parent <epic-id>

# Task with a dependency
bd create "Deploy auth" --deps "<impl-id>"

# Task with description
bd create "Issue title" --description="Detailed description here"
```

### Reading Issues

```bash
bd list                          # All issues (human-readable table)
bd list --json                   # JSON output
bd show <id>                     # Single issue details
bd show <id> --json              # JSON output for single issue
bd ready                         # Issues with no open blockers
bd dep tree <id>                 # Dependency graph (ASCII tree)
bd dep cycles                    # Detect circular dependencies
```

### Updating Issues

```bash
bd close <id>                              # Close an issue (direct — see note above)
bd update <id> --status in_progress        # Change status
bd delete <id> --force                     # Delete an issue
bd delete --from-file <path>               # Batch delete from file of IDs
```

### Epic Management

```bash
bd epic status <id>              # Completion percentage
bd epic close-eligible           # Find epics where all children are closed
```

## Concurrency Rules

Write operations must be sequential. In no-db mode, concurrent JSONL writes cause duplicate issues and data corruption.

| Operation | Safe in Parallel? | Risk if Parallel |
|-----------|-------------------|------------------|
| `bd list` | Yes | None (read-only) |
| `bd show` | Yes | None (read-only) |
| `bd ready` | Yes | None (read-only) |
| `bd create` | **NO** | Duplicate issues (verified: 5 parallel creates → 10 issues) |
| `bd close` | Tested safe, don't rely on it | Theoretically risky |
| `bd update` | **NO** | Last writer wins |
| `bd delete` | **NO** | Last writer wins |

### For Multi-Agent / Subagent Workflows

1. **Create all issues sequentially in the orchestrator** BEFORE spawning parallel subagents
2. Each subagent closes its own issue at the END of its work (sequential by nature)
3. **Never** have two subagents call `bd create` simultaneously

## What NOT to Do

| Don't | Why |
|-------|-----|
| Run `bd init --force` with existing data | **May zero backup JSONL files.** Verify `wc -l .beads/backup/issues.jsonl` is non-zero before AND after. |
| Set `BEADS_DB` environment variable | Forces a specific database mode. Leave it unset. |
| Run write commands in parallel | Duplicate issues, lost data. See concurrency rules. |
| Edit `metadata.json` manually | Corrupt JSON breaks bd operations. Let `bd init` manage it. |

## Recovery Procedures

### JSONL Files Lost or Corrupt

```bash
# 1. Check git history for last good version
git log --oneline -- .beads/backup/issues.jsonl

# 2. Restore from git
git show <good-commit>:.beads/backup/issues.jsonl > .beads/backup/issues.jsonl
git show <good-commit>:.beads/backup/events.jsonl > .beads/backup/events.jsonl
git show <good-commit>:.beads/backup/dependencies.jsonl > .beads/backup/dependencies.jsonl

# 3. Verify
bd list
```

### JSONL Parse Errors

```bash
# Validate each line
python3 -c "
import json
for i, line in enumerate(open('.beads/backup/issues.jsonl'), 1):
    line = line.strip()
    if line:
        try: json.loads(line)
        except json.JSONDecodeError as e: print(f'Line {i}: {e}')
"
```

### `bd show <id>` Says "Not Found" but `bd list` Shows It

Known intermittent issue with ID resolution. Workaround:

```bash
bd list --json | jq '.[] | select(.id == "<id>")'
```

### Duplicate Issues After Parallel Creates

```bash
# Find duplicates
bd list --json | jq -r '.[].title' | sort | uniq -c | sort -rn | head

# Delete extras
bd delete <duplicate-id> --force
```

## Config Reference

### .beads/config.yaml

```yaml
# Enable JSONL-native mode (no Dolt dependency)
no-db: true

# Git branch for bd sync commits (optional, for multi-repo sync)
sync-branch: "beads-sync"
```

### .beads/metadata.json

Auto-generated by `bd init`. Do not edit manually.

```json
{
  "database": "dolt",
  "backend": "dolt",
  "dolt_mode": "server",
  "dolt_database": "beth",
  "project_id": "<uuid>"
}
```

This file is vestigial from the Dolt era. In no-db mode, the `backend` and `dolt_*` fields are ignored. The file is still generated by `bd init` and should be left alone.

## Summary

| Question | Answer |
|----------|--------|
| Does bd need Dolt? | **No.** With `no-db: true`, all operations use JSONL directly. |
| Does `no-db: true` work? | **Yes.** Verified working in v0.60.0. Doctor confirms it. |
| Where is the data? | `.beads/backup/*.jsonl` — that's the live store. |
| Do I need to run `bd backup`? | **No.** In no-db mode, JSONL is written directly. |
| How do I close issues in Beth? | `npx beth-copilot close <id>` (enforcement layer). |
| Can I read JSONL with a text editor? | **Yes.** One JSON object per line. |
| Can agents write in parallel? | **No.** Sequential writes only. |
| Can agents read in parallel? | **Yes.** Reads are always safe. |
| What about the `.beads/dolt/` directory? | Vestigial. Pending cleanup (beth-ajg.6). Harmless. |
